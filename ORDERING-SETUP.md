# Noiric café workspace

Run npm install, then npm run dev. Existing visitor website is preserved.

## Pages
- /order: responsive menu, search/category/vegetarian filters, sorting, persistent cart, customer sign-in, order tracking, loyalty, music queue/votes/requests and QR scanner.
- /admin: password-protected workspace with sidebar, kitchen, menu editor, table QR printing, customers, music and settings.
- /kitchen redirects to /admin?view=kitchen.
- Generate real seat links in Admin → Tables & QR. A plain ?seat=10 only browses the menu. The opaque code is looked up server-side, and the numeric seat parameter is never trusted.

## Database and credentials
Migrations 001_ordering.sql and 002_cafe_workspace.sql are applied to the configured Supabase project. Server credentials remain in ignored .env.local. KITCHEN_PASSWORD controls staff access; SESSION_SECRET signs 12-hour staff sessions. Supabase access/refresh tokens stay in HTTP-only cookies. Tables are inaccessible to anon/authenticated direct requests; the Next server verifies each action before using its server-only service role.

For Vercel, add these variables under Project → Settings → Environment Variables, keeping `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `KITCHEN_PASSWORD` and `SESSION_SECRET` server-only (never prefix them with `NEXT_PUBLIC_`): `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `KITCHEN_PASSWORD`, `SESSION_SECRET`, and `RESEND_API_KEY`. Set optional `RESEND_FROM` after verifying a sending domain. Redeploy after adding variables. `.env.local` is ignored and must never be committed.

## Email OTP via Resend
`RESEND_API_KEY` is stored in ignored `.env.local` and used only by the server. Sign-in codes are generated by Supabase Auth's admin `generate_link` API, sent directly through Resend's HTTP email API, then verified by Supabase Auth. This avoids Supabase SMTP and its email template for this flow. The key is send-only; use Resend's dashboard to manage domains. Never expose the key in browser code, Git or chat.

The development sender is `NOIRIC <onboarding@resend.dev>`. Add and verify a café-owned sending domain in Resend before sending to all customers; then configure server-side `RESEND_FROM`, for example `NOIRIC <login@your-verified-domain>`. Do not use a sender domain you do not own. A real customer delivery has not been tested because no recipient address was provided.

Phone OTP is postponed: Supabase currently reports phone authentication disabled. Enable it later with an SMS provider, then the app will expose phone sign-in. Supabase supports providers such as Twilio, MessageBird and Vonage, or a custom Send SMS Auth Hook.

## Order and loyalty rules
Prices, availability, quantities, seat code and discounts are validated server-side. Orders use a stable request UUID to prevent duplicate submissions. Kitchen must explicitly verify the occupied table before accepting. Then mark ready, served and record the actual payment separately. Unpaid orders may be cancelled with a customer-visible reason; paid-order refunds are not implemented.

A visit counts once per India calendar day only after an order is both served and paid with a positive total. Five unallocated visit days within 30 days earn one reward, expiring after 30 days. Returning on a later day within the window can receive the configured discount. Admin → Settings selects the discount percentage and eligible reward dish. Defaults: 0% and no reward dish, so choose the actual business offer before rollout. A reward discounts one unit of that dish, is reserved during ordering, released on cancellation and redeemed after payment + serving. Rewards and return discounts do not stack. Mixed paid orders that use a free item still count if the final total is positive.

## QR and Wi-Fi
Table cards support PNG download and browser printing. Regenerating a table QR invalidates old prints. A printed QR is reusable and can be photographed; it does not prove physical presence. Customer sign-in, optional network checks and kitchen table confirmation mitigate this.

The admin can store Wi-Fi SSID/security/password and generate a separate Wi-Fi QR. Browsers cannot silently join Wi-Fi. Table-code and Wi-Fi scans are separate actions with device confirmation.
Wi-Fi order/vote/request enforcement is off by default and disabled locally. The current implementation supports Vercel's trusted x-vercel-forwarded-for header plus an explicit café public-IP allowlist, failing closed elsewhere. Configure/test fixed café egress IPs on actual hosting before enabling; do not simply set VERCEL=1 on another server. Shared ISP addresses and signal outside the café mean network checks still do not prove table occupancy.
https://vercel.com/docs/headers/request-headers

For phone tests, use the computer's LAN address :3000 on the same network instead of localhost. Camera access requires HTTPS or localhost; on plain LAN HTTP use the phone's native QR reader or upload a QR photo.

## Kitchen and music
Enable sound once to permit spoken new-order announcements; keep the admin open on the kitchen computer. Browser speech uses installed voices and is not a background notification service. Tickets refresh every 10 seconds; customers refresh every 12 seconds.
Verified customers at a valid seat can request tracks and vote; votes persist and are unique per customer/track. Admin adds/removes tracks and marks the current track. This is the requested music frontend and queue persistence: YouTube Music search, playback integration and automatic player control are not connected.
